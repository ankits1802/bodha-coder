# Load test

`coder_day.js` is a [k6](https://grafana.com/docs/k6/) 2.4.0 script that drives the API the way a
practice does over a working day: coders sign in, list the queue, open notes, and upload the day's
PDFs. It runs against **a local compose stack, or a host whose name contains `staging` or `stg`,
only**. `setup()` refuses any host that is not `localhost`, `127.0.0.1` or such a name, and there is no
switch to turn that off. Production at `www.bodhaai.co` is the only AWS environment, so today that means
the compose stack ([docs/DEPLOY.md](../../docs/DEPLOY.md#local-and-staging-with-docker-compose)). Never point
it at production: every upload creates notes and queues real Gemini reads.

## What it sends

| Scenario | Requests per iteration | Rate |
|---|---|---|
| `reviews` | `GET /api/notes`, then `GET /api/notes/{id}` for a random note on the first page | `NOTES_PER_DAY × READS_PER_NOTE ÷ WORKDAY_HOURS × PEAK_FACTOR` per hour |
| `uploads` | `POST /api/uploads` with `NOTES_PER_UPLOAD` synthetic one-page PDFs | `NOTES_PER_DAY ÷ NOTES_PER_UPLOAD ÷ WORKDAY_HOURS × PEAK_FACTOR` per hour |

Each virtual user signs in once with `POST /api/auth/login` and refreshes its session every ten
minutes. At the defaults (3,000 notes, 8 hours, 10 notes per upload, 4 reads per note) that is one
upload of 10 notes every 96 seconds and one queue-plus-note read every 2.4 seconds, which is the
3,000 notes/day target spread evenly. `PEAK_FACTOR=3` models the busiest hour.

The PDFs are generated by the script: each holds a unique synthetic line and the file name
`<yesterday> - LOADTEST SYNTHETIC - 99213 - Progress <marker>.pdf`. They contain no patient data.

Thresholds fail the run when more than 1% of requests or checks fail, or when the 95th percentile
exceeds 1.5 s for sign-in, 0.8 s for the queue and a note, or 8 s for an upload.

## Before a run

1. In the HQ of the stack under test, create a practice used only for load tests, with two-step verification not
   required for the coder role.
2. Invite a coder (or admin) to it and set the password. This account must be able to sign in
   without two-step verification.
3. Add one provider and note its id (`GET /api/providers` while signed in as that user).
4. Check the stack's Gemini budget and quota (none with `GEMINI_BACKEND=demo`): at the defaults a 15-minute run uploads about 95
   notes, and each one is read by the model.
5. On a shared stack, tell its owners first; alarms on queued analyses may fire.

## Settings

| Variable | Default | Meaning |
|---|---|---|
| `BASE_URL` | required | the web address of the stack under test, for example `http://localhost:3000` or `https://coder.staging.example.com` |
| `LOAD_EMAIL`, `LOAD_PASSWORD` | required | the load-test account |
| `LOAD_PROVIDER_ID` | required | the provider the uploads are filed under |
| `LOAD_PLACE_CODE` | `11` | place of service for the uploads |
| `LOAD_VISIT_TYPE` | `Established patient` | visit type for the uploads |
| `LOAD_BILLED_CODE` | `99213` | billed code written into each file name and detail |
| `NOTES_PER_DAY` | `3000` | daily volume to model |
| `WORKDAY_HOURS` | `8` | hours the volume is spread over |
| `NOTES_PER_UPLOAD` | `10` | PDFs per upload |
| `READS_PER_NOTE` | `4` | queue-plus-note reads per uploaded note |
| `PEAK_FACTOR` | `1` | multiplier on both rates |
| `DURATION` | `15m` | how long both scenarios run |

Sign-in is rate limited to 10 attempts per account and 30 per address in 15 minutes. The script
uses at most 9 virtual users, each signing in once, so keep one run at a time per account.

## Run

With Docker (no install):

```
docker run --rm -i --volume "$PWD/tools/load:/scripts:ro" \
  -e BASE_URL=https://coder.staging.example.com \
  -e LOAD_EMAIL=load-coder@example.com -e LOAD_PASSWORD -e LOAD_PROVIDER_ID=<provider id> \
  -e PEAK_FACTOR=3 -e DURATION=30m \
  grafana/k6:2.4.0 run /scripts/coder_day.js
```

Export `LOAD_PASSWORD` in the shell first so it never appears in the command history. With a local
k6 binary the same variables apply: `k6 run tools/load/coder_day.js`.

Against the compose stack use `BASE_URL=http://localhost:3000`; the refresh cookie is `Secure`, so
over plain HTTP each virtual user signs in again instead of refreshing.

## While it runs and after

- Watch `BodhaCoder/QueuedAnalyses` and `RunningAnalyses` in CloudWatch: queued should return to
  zero within a few minutes of each upload. A queue that only grows means the worker is the limit.
- Read the k6 summary: `http_req_duration` per `name`, `http_req_failed`, and the checks.
- Search the API log group for `"status":5` during the run window.
- Close the load-test practice in HQ when finished; its records stay until the purge date
  ([docs/OPERATIONS.md](../../docs/OPERATIONS.md#close-and-purge-a-practice)), so on a compose stack it is
  simpler to drop the database volume.
