# Architecture

## Processes

| Process | Command | Does |
|---|---|---|
| API | `uvicorn app.main:app` | authentication, tenants, uploads, review actions, provider links, exports |
| Worker | `python -m app.worker` | claims queued analyses (`FOR UPDATE SKIP LOCKED`), runs the review, stores results |
| Web | `next start` | the web client; proxies `/api` to the API; with `ADMIN_URL` set, keeps `/hq` on the admin host and practice pages on the main host (`src/proxy.ts`) |

Both Python processes share Postgres and the object store. The worker runs `AI_WORKERS` loops, a
recovery loop that re-queues analyses left running by a stopped worker, and a reminder loop every five
minutes: provider requests past their link expiry become `expired` (the note returns to its lane and a
held claim is released), and unanswered requests get at most two reminders, at 12 and 36 hours, each
with a fresh link. Once a day it deletes stored files that no record holds (the orphan sweep, below)
and removes access-log entries past their retention, never younger than 2557 days (Records, below).
Every 15 minutes it brings each live subscription's billed quantity in line with the practice's active
providers, or those of the organization's combined practices (Plans and billing, below), and every hour it tells the admins of a practice whose plan ends within
three days (Inbox, below). Every minute it reads the watched folders and the email that arrived for
intake (Intake, below).

With `SENTRY_DSN` (api, worker) or `WEB_SENTRY_DSN` (web) set, errors also go to Sentry, scrubbed to
exception types and stack frames; without them no SDK is started
([0047](decisions/0047-error-tracking-off-until-configured.md)).

## API types

Request bodies are pydantic models (`api/bodies.py`, `api/quality_bodies.py`). Services build each
response as a dictionary; the route declares its pydantic response model with `response_model=`,
from `api/responses/<area>.py`. The types flow one way:

| Step | Where | Rule |
|---|---|---|
| Route | `api/routes/<area>.py` | every JSON route names a response model. File downloads (claims CSV, defense packet PDF, addendum text) declare their media type with `responses.base.file_download`; the Google redirects declare `RedirectResponse`; 204 routes have no body |
| Validation | `responses.base.View` | `extra="forbid"`: a key the service builds but the model does not declare fails the request (500) and the test that reaches it, so the model and the service cannot drift silently |
| Errors | `responses.errors` | every non-2xx JSON body is `{"error", "message"}` (`ErrorResponse`, codes in `core.errors.ERROR_CODES`). Each operation documents `422` (takes input), `401` (needs a session), `403` (role guard) and `default`, read from its dependency tree; unknown routes, wrong methods and unhandled exceptions answer in the same shape, the last with a fixed message |
| Exact keys | `responses.base.ExactRoute` | every router uses it; it serialises with `exclude_unset`, so a response carries exactly the keys the service built. A key a service may leave out is declared `Omittable[...] = None` (optional in the schema, never `null`) |
| Document | `tools/export_openapi.py` | writes `frontend/openapi.json` (sorted keys, LF) from `app.main.app.openapi()` with placeholder settings, no database |
| Frontend | `npm run api:types` | `scripts/api-types.mjs` runs openapi-typescript on `openapi.json` and prints `src/lib/api/schema.ts` without comments |
| Screens | `src/lib/api/types.ts` | named aliases over `components["schemas"]` (`NoteDetail`, `QueueRow`, …) and the literal unions derived from them (`NoteStatus = NoteSummary["status"]`). Hand-written there: query and form types the client composes (`QueueQuery`, `UploadPlan`, `InviteBody`, …) and `MdmElements`, the reading of a finding's free-form `detail` |

CI regenerates both files (backend job: `openapi.json`; frontend job: `schema.ts`) and fails on any
difference. Decision: [0022](decisions/0022-typed-responses.md).

## Data model and revisions

Nothing a person or the model produced is overwritten or deleted while it must be kept: seven years
(2557 days) from creation, and seven years after a practice closes. Postgres enforces it with
triggers, database timestamps, hash chains and a least-privilege runtime role (Records, below).

| Table | Holds | Revisions |
|---|---|---|
| `notes` | one visit document: file, patient, date of service, provider, place, lane, headline, `impact_cents` (the estimated dollar change of the derived claim, set at each placement), `returned_at` (set while a compliance return is open, cleared by approval or a new flag); a voided note keeps `status_before_void`, `voided_at`, `voided_by` and `void_reason` | current state only; everything below is the history; never deleted |
| `note_changes` | each in-place change of a note with old and new value, reason, who and when: `status` (void, restore), `flag`, `payer`, `assignee`, `visit_type` | append-only |
| `note_returns` | each return of a note by compliance: the structured reason (`level_not_supported`, `documentation_missing`, `coding_error`, `ask_provider`, `payer_policy`, `other`), the optional note (required for Other, at most 500 characters), the flag it cleared, who and in which role, the current analysis and the finding keys that need a fresh decision ([0043](decisions/0043-one-findings-list-and-returns.md)) | append-only; the database refuses updates, deletes and truncation (migration 0018) |
| `note_texts` | the note's text: a `document` revision for each PDF (extracted text, or empty for a scan until the model's text is stored as the next `document` revision), then one per signed addendum. A read uses the texts from the latest `document` revision onward | append-only |
| `analyses` | one row per model run or re-derivation: inputs (context, with the billed codes' modifiers and units), model, prompt version, tokens (top-up calls included), `cost_microusd` and the `price_snapshot` it was priced at, validated report, raw response key, rendered prompt key and its SHA-256, `app_version`, `generation` (per call: model, schema SHA-256, temperature, schema applied), `document_key` | outcome and cost columns written once; older runs become `superseded`; never deleted |
| `analysis_failures` | each failed attempt of an analysis: attempt, error, whether it was retried | append-only |
| `suggestions` | each suggestion of an analysis: kind, codes before and after, action, reasoning, evidence quotes, severity, detail | belong to one analysis |
| `decisions` | each choice a person made on a suggestion, and each diagnosis-pointer choice for a claim line (`pointers:<code>:<diagnoses>`), with the person's role and, for a choice that departs from Bodha or a hand-linked pointer, `override_reason` and `override_note` | append-only; the latest per key applies; a reason given later is a new row |
| `code_sets` | billed and final code lists; a final procedure line carries its `pointers` when the coder linked them; a hand edit of billed codes carries its role, `override_reason` and `override_note` | append-only revisions per kind |
| `addendum_requests` | questions sent to a provider, the answers and the signed addendum; `purpose` `questions` or `level_change` (with `approved_claim_id`, the snapshot asked about) | one per request |
| `approved_claims` | the claim frozen at each approval: codes with resolved pointers, E/M line, diagnoses with letters, billed codes as uploaded and as reviewed, every decision with its reason, the approver (id, name, role) and time, the analysis, model, prompt version, note text revision ids, document key and SHA-256 (`content`, `schema_version` 1) | one revision per approval; the database refuses updates and deletes |
| `claim_exports`, `claim_export_items` | each claims CSV or claim lines download: format, who, role, when, address, device, the stored file's key, name, size and SHA-256; one item per note with its snapshot and revision | written once; the database refuses updates and deletes |
| `provider_attestations` | each provider signature or level answer: the wording ticked, the note text revision ids shown, the text signed or shown, the answer (`signed`, `confirm`, `disagree`), comment, address and device | written once; the database refuses updates and deletes |
| `review_comments`, `review_comment_removals` | comments on a finding key or the note (author, role, mentions) and the removal of one (who, role, when) | written once; a removal hides, never deletes; the database refuses updates and deletes |
| `audit_packages` | each audit package downloaded: stored key, SHA-256, size, file count, who, role, address, device | written once; the database refuses updates and deletes |
| `signatures` | each signature captured for a person (`user_id`) or a provider (`provider_id` with `practice_id`): source (`drawn`, `typed`, `uploaded`), typed name, image key, SHA-256, size, the Gemini check (or none for typed), address, device | written once; the database refuses updates, deletes and truncation |
| `signature_adoptions` | each time a person adopts a signature or a provider asks Bodha to remember one; the latest per owner is the signature in use | written once; the database refuses updates, deletes and truncation |
| `signing_events` | each signing (approval, compliance decision, provider addendum, provider level statement, sign-up agreement): the signer, typed name, role or credential, signature, document and record SHA-256s, time, address, device, verification `code`, the canonical `envelope`, its SHA-256, and the KMS `seal` with its key and algorithm | written once; the database refuses updates, deletes and truncation; removed only by a purge |
| `access_log` | every PHI read, change and export (who, what, when, from where); `actor_kind` is `user`, `provider` or `system` (intake and auto-approval); `chain_seq`, `prev_hash`, `row_hash` link each practice's entries | append-only, hash-chained per practice; entries past the practice's retention (7 to 10 years, never under 2557 days) are purged |
| `activity` | administrative changes (setup, team, MIPS list, practice measures by key and version, HQ), `changes` with before and after values for HQ practice updates | append-only, one hash chain; never deleted |
| `audit_chain_anchors` | where a purged chain prefix ended (chain, last sequence and hash, rows removed) | append-only |
| `recovery_codes` | hashed single-use two-step recovery codes per user | a new set marks the old one used; never deleted while the user exists |
| `practice_memberships` | one row per person per practice (unique `(user_id, practice_id)`): `role`, `status` (`invited`, `active`, `blocked`), `invited_by`, `created_at`, `ended_at`; `realm` is fixed to `practice` and joins `users (id, realm)`, so HQ accounts hold none ([0037](decisions/0037-multi-practice-membership.md)) | current state; a removal, a leave or closing the practice sets `ended_at` and the row stays (never deleted, removed only by a purge); the history is in `access_log` |
| `auth_events` | every sign-in attempt and account security event: `kind`, `realm`, user and practice when known, SHA-256 of the lowercased email for failed sign-ins, IP, user agent, a short detail; never an email, password, code or token | append-only (stamped by Postgres, refused updates and deletes); practice rows follow the practice's access-log retention and the rest is kept 2557 days; each event of a known person is also written to that person's practices' access logs or HQ activity, which are hash-chained |
| `users.last_practice_id`, `sessions.practice_id` | the practice a person last worked in (where sign-in lands) and the practice each refresh session is in | changed by sign-in and a switch |
| `users.realm` | the account space: `hq` for the `hq` role, `practice` for every other role, computed by Postgres from `role`; an email is unique within a realm, so one person can hold an HQ account and a practice account under one email. `users.practice_id` and `users.role` are kept only for the release before 0013 and are never read for practice access | computed |
| `user_identities` | the sign-in service subject bound to a user (`provider` `google`, `microsoft` or `yahoo`, `subject`, and the user's `realm`, which a foreign key on `(user_id, realm)` keeps equal to the user's); one per user and provider, one user per provider subject in each realm | added on first use, deleted with the user |
| `inbox_items` | one item per person and practice: `kind`, note id when there is one, actor name and id, a payload limited per kind (`services.inbox.PAYLOAD_KEYS`, no PHI), `read_at` | `read_at` set once when read; removed only by `bodha_purge_practice` |
| `queue_views` | a person's saved queue views in a practice: name (unique per person and practice) and filters | added and deleted by the person (a preference, not a record); removed with the practice by `bodha_purge_practice` |
| `person_tours` | each tour a person finished or skipped: `user_id`, `tour` (`practice` or `hq`, the realm of the user), `version`, and `completed_at` or `skipped_at` (exactly one); primary key user, tour and version | written once: the first outcome of a version is kept; deleted with the user |
| `practices.confirm_level_changes`, `practices.hold_until_confirmed` | ask the provider to confirm an approved E/M level that differs from the billed one, and hold the claim from export until they do; both off by default | current setting; changes in `activity` |
| `practices.closed_at`, `closed_by`, `purged_at` | when HQ closed the practice (stamped by Postgres, final) and when its records were purged | written once |
| `practices.signup` | how the practice began: `{"source": "hq"}`, or for self sign-up `source` `self`, `agreement_version`, `accepted_at`, `accepted_by` (user id), `method` (`email` or the provider) and `ip` | written once when the practice is created |
| `rate_events` | one row per counted attempt (bucket, hashed key, time) | deleted once outside the window |
| `intake_addresses` | a practice's email intake address: random `local_part` (16 base32 characters), who made it, `retired_at` and `retired_by`; at most one unretired per practice | columns written once (`bodha_write_once`); never deleted, removed with the practice by `bodha_purge_practice` |
| `intake_senders` | an allowed sender of a practice: `pattern` (an address, or a domain without `@`), `kind` (`address`, `domain`), who added it, `removed_at` and `removed_by`; unique while not removed | columns written once; never deleted, removed with the practice by a purge |
| `intake_messages` | one row per email and address: SES message key, practice and address (none for an unknown address), received time, the single `From` address (none for an unknown address), `outcome` (`accepted`, `refused`, `test`), `reason` when refused, accepted and refused file counts, per file the SHA-256, size, outcome, reason and note id, and the SES verdicts; never a subject, body or file name | append-only (refused updates, deletes and truncation); unique per message key and address |
| `intake_tests` | each Send a test: practice, address, SHA-256 of the token in the subject, who sent it, and once it arrives `arrived_at` and the message | columns written once; removed with the practice by a purge |
| `organizations` | a group of practices: name, `status` (`active`, `closed`, `purged`), the combined `plan` and `renews_on`, `closed_at` (stamped by Postgres, final), `closed_by`, `purged_at` ([0044](decisions/0044-organizations-and-domain-join.md)) | current state; never deleted (a purge leaves the row as a tombstone) |
| `practices.organization_id`, `practices.combined_billing` | the organization a practice belongs to (at most one) and whether the organization pays for it; a combined practice carries the organization's plan and renewal, copied whenever they change | current state; changes in `activity` |
| `organization_memberships` | organization admins: person, organization, `role` (`admin`), `added_by`, `ended_at`; `realm` fixed to `practice` | current state; removal and closing set `ended_at`; never deleted, removed only by `bodha_purge_organization` |
| `domain_claims` | an email domain claimed for a practice (by its admin, or by an organization admin with `organization_id`): random TXT token, the emailed link's hash, address and expiry, `verified_at` and `verified_via` (`dns`, `email`), `join_mode` (`off`, `request`, `auto`), `join_role`, `released_at`; one verified and unreleased claim per domain | current state; never deleted, removed with the practice or organization by a purge; history in `access_log` and `activity` |
| `domain_join_requests` | each request to join through a claimed domain (`pending`, `approved`, `declined`) and each automatic join (`joined`): claim, practice, name, email, role, the account, who decided and when | current state; never deleted, removed with the practice or organization by a purge |
| `subscriptions` | a paid subscription of one practice or one organization (`practice_id` or `organization_id`, exactly one; one each): `provider` (`stripe`, `paypal`), customer and subscription ids, `plan`, `interval` (`monthly`, `annual`), `status` (`pending`, `active`, `past_due`, `canceled`, `expired`), `current_period_end`, `cancel_at_period_end`, `quantity`, `past_due_since` | current state, written only from verified webhooks and the quantity sync; history in `activity` |
| `billing_events` | each processed Stripe or PayPal webhook (primary key provider and event id, kind, received) | append-only; a repeat is ignored |
| `remittances` | one 835 payment (ST/SE transaction) of an uploaded file: payer, payment date, file key, the file's SHA-256 (`file_sha256`) | one per payment; a file with several payments shares its key |
| `remittance_lines` | each service line paid: claim reference, patient, date of service, billed and paid codes and amounts (cents), CAS adjustments, status, the plan type whose appeal window applies (`appeal_plan_type`, appealable lines only), matched note; `appeal_by` holds the date written by uploads before migration 0007 | written once at upload |
| `audit_runs` | one blind audit or training set: purpose, scope, provider or specialty, period, notes requested, who started it, status (`done` once every note is coded) | one per draw |
| `audit_samples` | each sampled note of a run (`run_id`): reviewer, position, the frozen Bodha and claim references, the answer and its agreement | coded once |
| `practice_measures` | each version of a quality measure a practice defined itself: `measure_key` (`P001` to `P999`, never a CMS number), `version`, name, the practice's identifier, what puts a visit in scope and out of it, what the note must document to meet it, codes to report when met and when not met, `retired`, `created_by` ([0045](decisions/0045-practice-measures-and-usage-timing.md)) | append-only: an edit or a retirement is the next version; the database refuses updates, deletes and truncation (migration 0020); removed only with the practice by `bodha_purge_practice` |
| `usage_events` | usage timing without patient data: practice, person, the session's role, the browser's event id, `kind` (`task` or `stall`), `task` (`note_review`, `queue`, `upload`, `billing_export`), for a task its `outcome`, visible duration, time to first decision and counts of key and pointer inputs and of findings decided by keyboard or pointer, for a stall its `step` and length | append-only (stamped by Postgres, refused updates, deletes and truncation; migration 0020); a resent event id is ignored; removed only with the practice by `bodha_purge_practice` |

The models declare no ORM relationships, so a flush does not order inserts by foreign key and ids
are assigned at flush: flush a new row before adding rows that reference it.

The queued `analyses` row is the job. The worker records `attempts`, the latest `error` and timing on it,
and one `analysis_failures` row per failed attempt.

## Object storage (S3 or R2)

| Key | Content |
|---|---|
| `practices/{practice}/notes/{note}/document.pdf` | the uploaded PDF |
| `practices/{practice}/notes/{note}/document-r{revision}.pdf` | an amended PDF that replaced it; `revision` is its `note_texts` revision. Earlier PDFs are kept |
| `practices/{practice}/notes/{note}/analyses/{revision}.json` | every raw model reply of that analysis |
| `practices/{practice}/notes/{note}/analyses/{revision}.prompt.json` | every request of that analysis exactly as sent (system instruction, rendered prompt, schema, temperature) and the document key and SHA-256; `analyses.prompt_sha256` is the SHA-256 of these bytes |
| `practices/{practice}/exports/{export}.csv` or `.json` | the exact bytes of a claims export, as downloaded |
| `practices/{practice}/notes/{note}/audit-packages/{package}.zip` | an audit package as downloaded |
| `practices/{practice}/remittances/{remittance}.835` | an uploaded 835 file as received (the id of its first payment) |
| `practices/{practice}/inbox/{provider folder}/{YYYY-MM-DD}/{file}.pdf` | a PDF dropped for automatic intake, named by the practice until the first poll that sees it renames it to `{sha256}.pdf` (`{sha256} - {CPT}.pdf` when the name carried a CPT code) in the same folder; moved out once read |
| `practices/{practice}/evaluations/{run}/{case}-{attempt}.json` | the raw replies of each read of an evaluation case |
| `practices/{practice}/inbox/processed/{day}/{sha256}.pdf` | a dropped PDF that became a note (the note keeps its own copy) |
| `practices/{practice}/inbox/rejected/{day}/{sha256}{ext}` and `….reason.txt` | a dropped file that was refused, and the reason with its path after renaming |
| `ses-inbound/{message}` | in the inbound mail bucket (`EMAIL_INTAKE_BUCKET`), not the documents bucket: a raw email stored by SES for email intake (`{message}` is the SES message id); deleted by the worker once kept and recorded, and expired after 14 days if never read ([0046](decisions/0046-email-intake.md)) |
| `ses-inbound/{message}.json` | in the inbound mail bucket: its envelope from the intake function: envelope recipients and SES verdicts ([infra/ses_intake](../infra/ses_intake/README.md)); deleted with the message |
| `ses-retained/{message}` | every raw email received for intake, copied by the worker before it reads it |
| `archives/practices/{practice}/access-log.csv` | a purged practice's whole access log with its chain columns; its SHA-256 is in HQ activity |
| `people/{user}/signatures/{signature}.png` | a person's captured signature (one set per person across practices); removed when a purge removes the person |
| `practices/{practice}/signatures/{signature}.png` | a provider's signature captured on the secure link |

Keys carry ids only, never names. PDFs are opened through signed links that expire after
`PDF_LINK_SECONDS`. The bucket is meant to run S3 Object Lock in governance mode with seven-year
retention, so no stored object version can be removed before then without a separate bypass permission.

## How a note flows

1. `POST /api/uploads/preview` reads page 1 of each PDF and proposes provider, date of service, place
   and patient with a confidence (Upload matching, below). `POST /api/uploads` takes each file's provider,
   date and place (the form's fields are defaults), validates every file first (placement, PDF signature,
   size, billed codes), stores the PDFs, and creates one batch per provider, date and place, with notes,
   billed code set revision 1 and a queued analysis each.
2. The worker claims the analysis, takes the note texts from the latest `document` revision onward
   (or extracts the PDF text), attaches the original PDF so the model can read its layout while quoting only from the text (a scan with no text layer goes as the PDF alone), and calls `ai.review.review_note` with the
   practice's enabled checks, the setting from the place of service, the billed codes and the
   practice MIPS scope (the CMS measures on its list and the latest version of each measure it defined itself).
3. `services.findings.build_findings` turns the report into suggestions. Every suggested ICD-10-CM
   code must be billable in the release for the date of service; every CPT code must be on the CMS
   fee schedule list or an E/M family; every modifier must be in the allowed set for its code;
   otherwise the suggestion is marked for review.
4. `services.routing.place` chooses the lane: compliance (flagged, a Critical audit risk, or the
   visit level two or more levels too high and not cleared), waiting on the provider, returned by
   compliance (needs a coder with reason `returned`, until approved or flagged again), needs a coder
   (any code change), questions to send, or ready to approve. When the billed list has no ICD-10-CM
   code (`billed_diagnoses=False`), documented supported diagnoses join the claim without counting as
   code changes.
5. People decide. The claim is always derived: billed codes plus the latest decision on each
   suggestion, with the latest diagnosis pointers on each procedure line. A choice that departs from
   Bodha needs a reason (Review audit trail, below). Approval writes a final code set revision and an
   approved claim snapshot. Until export an approval can be undone (`POST /api/notes/{id}/reopen`, or
   `POST /api/notes/reopen` for several, all or none); the final code set and the snapshot stay as
   history and `reopened` is logged.
6. Asking the provider stores the questions and emails or texts a link whose token travels in the
   URL fragment. The provider confirms a one-time code sent to the contact on file, answers, and
   signs; the answers become a new note text revision and a new analysis is queued.

## Records: replaced PDFs, retention, voids and closing a practice

| Piece | Flow |
|---|---|
| Replace a PDF | `POST /api/notes/{id}/document` (uploaders; `services.records.replace_document`). Refused for an exported or voided note, a note being read, an open provider request, a file that is not a PDF or is too large, the same file, or a file another note already holds. The new PDF is stored under `document-r{n}.pdf` and becomes `notes.file_key`; the old object stays. A `document` text revision `n` holds the extracted text, or an empty string for a scan. Queued analyses of the note become `superseded`, a new one is queued with reason `document`, the note returns to `queued` (an approval is cleared) and the access log records `replaced PDF`. The note view shows the texts from the latest document onward |
| Void a note | `POST /api/notes/void` `{note_ids, reason}` (uploaders; `services.note_voids.void_notes`): status `voided`, the earlier status in `status_before_void`, `voided_at`, `voided_by`, `void_reason`; queued analyses become `superseded`; one `note_changes` row and `voided note` in the access log per note; every row and file stays. A coder voids only a note never read (`queued` or `failed`, no current analysis); an admin any note but one being read; a note with an open provider request is refused. Voided notes leave every work list, count and batch total; search still finds them. `POST /api/notes/{id}/restore` `{reason}` (admins) puts the earlier status back (queued means a new read), refused while another note holds the same PDF; `uq_notes_practice_file` lets a voided PDF be uploaded again |
| Access-log retention | `practices.access_log_years`, 7 (default) to 10, set by an admin on Settings, Security (`PUT /api/practice/security`). `services.retention.purge_access_logs(db, now)` asks `bodha_purge_access_log(practice, cutoff)` per practice, the cutoff being the earlier of the start of the practice-local day that many years before `now` and the database time minus `RETENTION_DAYS`; the function refuses a cutoff later than 2557 days before its clock, removes a prefix of the practice's chain and writes an `audit_chain_anchors` row. `bodha_purge_auth_events` removes the practice's `auth_events` before the same cutoff, and those of no practice 2557 days back, under the same floor. The worker calls them once a day |
| Close a practice | HQ only, after the practice is `ended` or `blocked` and has no live subscription: `POST /api/hq/practices/{id}/close` `{confirm_name}`. `services.retention.close_practice` ends every member's sessions in the practice and their memberships (`ended_at`), cancels open provider requests, supersedes queued analyses, sets status `closed` and `closed_at` (Postgres stamps it; trigger `bodha_closure` keeps it final) and writes `practice closed`. Every row and file stays; sign-in and intake stop because the practice is not open |
| Purge a practice | HQ only: `POST /api/hq/practices/{id}/purge` `{confirm_name}`, refused until `RETENTION_DAYS` (at least 2557) after `closed_at` by the database clock. `services.retention.purge_practice` writes the access log with its chain columns to `archives/practices/{id}/access-log.csv`, calls `bodha_purge_practice` (`SECURITY DEFINER`; deletes the practice's rows in foreign-key order: signing events, signature adoptions and signatures, with those of the people leaving with it (migration 0017), review records, returns to the coder (migration 0018), note children, addendum requests, approved claims, analyses and code sets, notes, batches, providers, MIPS list, access log, subscription, its inbox items and saved queue views and those of the people leaving with it (migration 0016), its domain join requests and domain claims (migration 0019), the sessions and auth events in it, its memberships, and the accounts, tokens, recovery codes and identities of people who belong to no other practice and administer no organization (their tours go by cascade); it marks the practice `purged`, the row staying), writes `practice purged` with the rows removed and the archive's entry count and SHA-256, and then removes every object under `practices/{id}/` and the stored signatures (`people/{user}/`) of the people it removed. | Orphan sweep | `services.file_sweep.sweep_orphan_files(db, store, now) -> int` (objects deleted), once a day from the worker under a Postgres advisory lock on its own connection, so one worker sweeps at a time. ## Security

Access tokens live in memory and carry a version, the active practice and the role in it; a password
set or a two-step reset bumps the version and revokes refresh sessions, and every request re-reads the
membership, so a block or removal in one practice ends access there at once and a role change answers
401 until the client refreshes. Refresh tokens rotate on every use,
are stored hashed, and expire after inactivity. Two-step verification (TOTP) is required for HQ and
for the roles each practice chooses (admins by default). Every route states the roles it accepts; every practice query
filters by the caller's practice. Provider sessions are a separate token type valid for one request.

| Piece | How it works |
|---|---|
| Hosts and realms | with `ADMIN_URL` set, HQ lives on its own host ([0033](decisions/0033-hq-on-its-own-host.md)). `core.realms.request_site` reads the request's host (the `Host` header, or `X-Forwarded-Host` when `Host` is not one of the two configured hosts and the peer is in `FORWARDED_ALLOW_IPS`, which is how the web server's `/api` rewrite arrives) and answers a `Site`: the `ADMIN_URL` host serves the `hq` realm, every other host the `practice` realm on `APP_URL`; with `ADMIN_URL` empty one site on `APP_URL` serves both. Login, the two-step steps, refresh, forgot and set password, the sign-in services and every authenticated request accept only users of the site's realms (`session_actor` answers 401 otherwise), so the same email or the same Google, Microsoft or Yahoo subject reaches a different account on each host. Self sign-up exists only where the `practice` realm is served. Emailed links use `ADMIN_URL` for HQ users and `APP_URL` for practice users (`core.realms.realm_url`). Session cookies carry no `Domain`, so each host keeps its own. With `ADMIN_URL` empty both realms share one account space, as before: creating an account refuses an email either realm uses, and an email that matches two accounts signs in to neither |
| Sign-in policy | `services.auth.sign_in_user` is the one place that decides, after a password or a Google identity, whether two-step is needed (`mfa_enabled`, HQ, or the membership role in the landing practice's `mfa_roles`, `core.deps.needs_two_step`) or a session starts. Three read-only checks back the claim a practice bills. None of them writes a review record; each
read is written to `access_log`.

| Audit defense packet | `GET /api/notes/{id}/defense-packet` (note readers, practice scope through `note_for`). `services.defense_packet` gathers the note, provider, place, billed and final code sets (the derived claim while not approved), the Medicare national estimate, the E/M finding (MDM elements and justification, or documented time), every change-kind suggestion whose latest choice is accept, keep or add with its reasoning, override reason and verbatim evidence, the code-set checks (ICD-10-CM release for the date of service, CMS fee schedule code list, CMS-HCC V28 when the risk summary exists), every provider request with its answers and the signed addendum labelled as an amendment with its signing time, the decision history (decisions and code-set revisions with their reasons, and the note's decision actions in `access_log`) and every analysis run with model and prompt version. `services.defense_records` adds the note text, the suggestions not followed with their reasons, the suggestions of earlier runs, flag and compliance reasons, the approved claim snapshots, exports, provider statements and comments (laid out by `services.defense_record_layout`). `services.defense_layout` turns that into blocks and `adapters/pdf_writer.py` renders them with reportlab (Helvetica). | Parser | `services/x12.py` reads the envelope strictly: the separators from the fixed-width ISA, ISA/IEA, GS/GE and ST/SE nesting, control numbers and counts. `services/remittance_835.py` reads BPR, TRN, DTM*405, N1*PR (and REF*2U), CLP, NM1*QC, DTM*232/472, SVC and CAS, and refuses a service line that does not balance (SVC02 − CAS = SVC03) or a payment that does not (Σ CLP04 − Σ PLB = BPR02). Errors are 422 with the segment named |
| Codes | per X12, SVC01 is the code the payer adjudicated and SVC06 the code submitted when it differs: billed = SVC06 or SVC01, paid = SVC01 |
| Matching | CLP01 is matched to a note id (the export carries it; a prefix of at least 8 characters, as payers may truncate to 20, when unique) and must agree with the date of service; otherwise patient name tokens (order and initials ignored) + date of service + billed CPT in the latest final (else billed) code set, when exactly one note fits |
| Status | `remittance_outcomes.line_outcome`: `denied` (CLP02 = 4, or nothing paid and nothing left to the patient), `downcoded` (paid a lower level of the same E/M family, or CO-150 / CO-152), `paid_as_billed`, `matched` (shown as Other: a different code, a reversal); a line with no note is `unmatched` |
| Appeal by | for denied and downcoded lines: payment date (BPR16, else DTM*405) + the window for the plan type. The plan type is Medicare for CLP06 MA/MB, Medicaid for MC, otherwise the practice payer list's type for the payer id or name, otherwise commercial. Windows default to Medicare 120 days (redetermination), Medicare Advantage 60 and 180 for the rest; admins change them with `PUT /api/remittances/appeal-days`. A line stores its plan type and the date is computed whenever lines are read (`remittance_outcomes.line_appeal_by`: list, detail and letter), so a change of window moves every date at once; a line stored before plan types keeps its stored `appeal_by` |
| Appeal letter | `GET /api/remittances/lines/{id}/appeal` re-reads the stored file for the member id and payer claim number and returns plain text (`services/appeal_letters.py`: redetermination for Medicare, reconsideration otherwise) with `defense_packet` = `/api/notes/{note}/defense-packet`. Writes `drafted appeal` |
| Screen | `/billing/remittances` (Billing, Remittances; billers): files with status counts and the first appeal-by date, the selected file's lines with filters (downcoded, denied, unmatched), and the letter with copy, download and the defense packet. Viewing lines writes `viewed remittance` |

## Upload matching

| Piece | How it works |
|---|---|
| Preview | `POST /api/uploads/preview` (uploaders, multipart `files`, at most 100): each file passes `check_pdf`, page 1 is read with `adapters.pdf_text.read_first_page_text` (an unreadable or scanned page reads as empty) and `services.upload_matching.match_file` proposes provider, date of service, place and patient, each with a confidence; `overall` is the weakest of provider, date and place and `check` is true below 0.8. ## Intake

A practice can drop PDFs into its own prefix, or email them, instead of uploading them.

### Watched folder

| Piece | How it works |
|---|---|
| Settings | `practices.intake`: `enabled`, `prefix` (`inbox` or `inbox-…`, always under `practices/{practice}/`), `provider_by_folder` (folder → active provider), `place_code`, `visit_type`. `GET` and `PUT /api/practice/intake` (admins) answer exactly these, never the storage path; the admin section is `components/shared/intake/IntakeSettings.tsx`, which shows whether PDFs are being read. Writes `intake saved` |
| Layout | `practices/{practice}/inbox/{provider folder}/{YYYY-MM-DD}/{file}.pdf`; the day folder is the date of service. `processed` and `rejected` are reserved folder names |
| Poll | `services.intake.poll_intake(db, store, now) -> int` (notes created), with a `ListingStore` (`adapters/object_listing.S3ListingStore`). Each enabled, open practice is polled under a Postgres advisory lock held on its own connection (`pg_try_advisory_xact_lock`), so two workers never ingest the same practice at once. Files are grouped by folder and day; every file is first renamed in its folder to `intake.arrival_name`: the SHA-256 of its content, ` - {CPT}` when the name carried a CPT code, and its suffix, so a patient name in a file name lives at most one poll; a name already of that shape is kept. Then each is checked with the upload checks (`uploads.check_pdf`, `uploads.billed_codes_for`, codes from the renamed file name) and each group goes through `uploads.create_intake_upload` as one batch: `batches.source` `intake` with no `created_by`, billed code sets with no actor, and the `uploaded notes` access entry by `Bodha intake` (`audit_log.record_system_access`, actor id `bodha-intake`, kind `user` because the access log allows only user and provider). Upload history shows Intake as the uploader |
| Results | accepted files move to `inbox/processed/{day}/{sha256}.pdf`; files in the wrong place, of the wrong type, for an unmapped folder, a future date, a failed check or a duplicate move to `inbox/rejected/{day}/` with a `.reason.txt`. Writes the `uploaded notes` access entry and an `intake processed` activity with counts |

### Email

A practice can email or forward PDFs to its own address instead
([0046](decisions/0046-email-intake.md)).

| Piece | How it works |
|---|---|
| Address | `POST /api/practice/email-intake/address` (admins) issues `{16 base32 characters}@{EMAIL_INTAKE_DOMAIN}` and retires the current one; `DELETE` retires it (email intake off). `GET /api/practice/email-intake` answers `available` (whether Bodha has an intake domain), the address and since when, earlier addresses and the allowed senders. Writes `email intake address issued` and `email intake address retired` |
| Senders | `POST /api/practice/email-intake/senders {sender}` allows an address or a whole domain (a public mail service only by address; 409 for one already allowed; at most 100); `DELETE …/senders/{id}` removes one, keeping the row. Writes `email intake sender added` and `removed` |

A message with no accepted file is refused as `files_refused` |
| Test | `POST /api/practice/email-intake/tests` (five an hour per practice) emails the current address from `MAIL_FROM` with `Bodha intake test {id}.{token}` in the subject and stores the token's SHA-256; the message that carries it is recorded as `test` and sets `arrived_at`, read by `GET …/tests/{id}`. Writes `email intake test sent` |

## Quality programme

Bodha's accuracy is measured by people who cannot see what Bodha suggested, and autonomy is earned from
those measurements.

| Piece | How it works |
|---|---|
| Blind audit | `POST /api/quality/samples` (admin, compliance): `services.audit_samples.draw_sample` draws N approved or exported notes for the practice, a provider or a specialty with a date of service in the period (default 40, 150 for a specialty), shuffled with a seed recorded in the activity entry, and assigns them round-robin to the chosen reviewers, never to the person who approved the note. The draw is one `audit_runs` row (purpose, scope, provider, specialty, period, requested, `created_by`, status) and each note one `audit_samples` row with its `run_id` (`purpose` `audit`) and `result.position`. At drawing time `result.reference` freezes Bodha's suggested claim (billed codes with every suggestion at its default choice, from the current analysis, whose id is `analysis_id`) and the final claim. The run id is the sample id of every route. Writes `started blind audit` with the note count and seed |
| Blind form | `/insights/quality/review/{sample}` and `/training/{sample}` (note readers, reached from Assigned to you on Today and Training). `GET /api/blind-review/{sample}/next` returns only the next open item of the caller: its id, position and the current note texts; `GET /api/blind-review/items/{item}/document` signs the PDF link. Nothing else about the note leaves the server. `POST /api/blind-review/items/{item}/answer` checks the E/M code, every ICD-10-CM code (billable in the release for the date of service) and the modifiers, stores the answer, compares it with both frozen references (`services.agreement.compare_elements`) and marks the run `done` when no item is left open (under a row lock on the run). While the caller has an open item for a note, `api/blinding.SightedReader` and `SightedDecider` (`blind_review.refuse_blind_note`) answer 403 "This note is in your blind audit" on `GET /api/notes/{id}`, its `/document`, `/defense-packet`, `/claim-checks`, `/day` and `/addendum.txt`, and on `PUT /api/notes/{id}/decisions` and `/billed-codes`; other users are unaffected. Writes `opened note for blind review` and `coded note blind` |
| Agreement | `services.agreement`: per note, E/M exact match and its direction (`higher`, `lower`, `family`, `absent`), ICD-10 matched, compared and reference counts with missing and extra codes, exact modifier set match. `summarize` gives Wilson 95% rates (`core.statistics.wilson`) for the per-note measures (E/M exact, Bodha higher, Bodha lower, ICD-10 exact set, modifiers) and per-note bootstrap 95% intervals (`core.statistics.bootstrap_ratio`: 2,000 resamples of the notes, fixed seed, 2.5th and 97.5th percentiles) for ICD-10 precision and recall, with their F1. `visit_agreement` is the E/M exact rate alone |
| Results | `GET /api/quality/samples` lists the runs of the practice with progress, status, reviewers, `started_by` and the E/M exact rates; `GET /api/quality/samples/{sample}` (admin, compliance): the summary against Bodha and against the final claim, the same per provider, and one row per note; the references of a note stay hidden until it is coded. Writes `opened audit results`. Screen: `/insights/quality` (Insights, Quality, Blind audits), chart and table views; admins assign training sets under its Training view |
| Evaluation set | `POST /api/quality/eval-cases` (admins) marks an approved note: `eval_cases.expected` holds the final claim, its E/M code, MDM level, ICD-10 codes and modifiers, and the analysis it came from |
| Evaluation run | `POST /api/quality/evaluations` (admins) queues an `eval_runs` row with `GEMINI_MODEL` and `PROMPT_VERSION`. The worker calls `services.evaluation_runs.run_next_evaluation` (or `run_evaluation(db, run_id, deps)`), which claims the row `queued` → `running` with `FOR UPDATE SKIP LOCKED`, rebuilds each case's review inputs from its analysis context, the billed claim as uploaded (code set revision 1 through `code_sets.original_codes`, so a coder's billed-code edit never becomes the input) and current note texts without writing to the note, runs `deps.review` twice, derives Bodha's claim from each report with `build_findings` and `claim`, stores the raw replies under `practices/{practice}/evaluations/{run}/{case}-{attempt}.json`, and records per case the agreement of the first read with the expected claim and of the two reads with each other. A case the model cannot read keeps its error; a run with no scored case is `failed` |
| Gold set | `tools/gold_set/`: 48 synthetic notes with expected claims by construction (`cases.json`, validated against the code sets by `gold_checks.py`), `render_notes.py` (PDFs into the ignored `tools/gold_set/out/`), `load_gold_set.py` (loads them into an evaluation practice through the public API, idempotent by the case id in the file name) and `report_gold_set.py` (methods and results of the latest run). Runbook in OPERATIONS.md; decision [0049](decisions/0049-synthetic-gold-set.md) |
| Drift | `GET /api/quality/evaluations` lists runs with the model and prompt version and compares each finished run with the previous one: E/M exact, ICD-10 F1 or modifier agreement more than five points lower is `dropped`. `GET /api/quality/level-mix` compares the MDM level of Bodha's suggested E/M code on notes seen in the last 30 days with the 90 days before (chi-square test of homogeneity, sparse levels pooled, `shifted` below p 0.05, `not_enough` under 30 notes a window) |
| Earned autonomy | `services.autonomy.provider_eligibility`: the provider's notes in the latest `done` audit run that contains them (by its last coding time) must number at least 30, with the Wilson 95% lower bound of E/M exact agreement at least 90% and Bodha higher on at most 5%. `PUT /api/quality/providers/{id}/auto-approve` (admins) turns `providers.auto_approve` on only then. `services.auto_approval.auto_approve_eligible(db, note)` also needs the note ready in the approve lane with reason `matches`, never flagged or through compliance, no review items or critical audit risks, no open questions or sent request, the provider still eligible, and the note not one of the one in ten held for a person (`held_for_quality_check`: first eight hex digits of SHA-256 of the note id, modulo 10). `auto_approve(db, note)` writes the final code set with reason `auto` and no actor, and an `approved` access entry by `Bodha (auto)`; the caller commits |
| Training | `POST /api/training/sets` (admins) draws a set with `purpose` `training` for one trainee (an `audit_runs` row like an audit). `GET /api/training` lists every run with items assigned to the caller with running scores against the final claim; after each answer `GET /api/blind-review/items/{item}/feedback` shows the trainee's codes, the final claim, Bodha's suggestion and the suggestions with their evidence. Writes `opened training feedback` |

Decision: [0020](decisions/0020-measured-accuracy-and-earned-autonomy.md).
